### 사용자 스토리 : 회원이 주문을 마친다
### 시나리오 - 주문을 마치면 상대방에게 카카오톡 메시지가 전송된다

### 고른 기준 
- **잘못된 동작을 하는 로직을 판단가능한 시나리오다.**
- **해당 도메인의 핵심 기능이다.**

> ⚠️ 이 시나리오는 "🚧 현재 코드와 불일치"다. 지금 코드로는 테스트가 실패하는 것이 맞다. 아래는 **목표 동작**(받는 사람에게 전송)을 기준으로 쓴다.

#### 테스트 데이터 전략

| 데이터 | 준비 방법 | 이유 |
|---|---|---|
| 주문자 + 서비스 토큰 | `KakaoLoginClient`를 목으로 바꾸고 카카오 로그인 콜백(`GET /api/auth/kakao/callback?code=test`)을 호출한다. 목은 가짜 카카오 액세스 토큰과 테스트용 이메일을 돌려준다 | Given이 "카카오 로그인으로 서비스 토큰을 받았다"이므로 실제 로그인 흐름(회원 생성 → 카카오 액세스 토큰 저장 → 서비스 토큰 발급)을 그대로 거친다. 카카오 서버와 통신하는 부분만 바꾼다 |
| 주문자 포인트 | 로그인 뒤 `MemberRepository`로 회원을 찾아 `chargePoint`로 주문 금액보다 넉넉히 충전한다 | 카카오로 처음 가입한 회원은 포인트가 0이라 그대로는 결제가 안 된다. 포인트는 이 시나리오의 검증 대상이 아니다 |
| 받는 사람 | 카카오 로그인한 두 번째 회원을 같은 방법으로 만들고, 그 회원 ID를 주문 요청의 `receiverId`로 보낸다 | 메시지가 주문자가 아니라 **다른 사람**에게 갔는지 구분하려면 받는 사람이 따로 있어야 한다 |
| 카테고리, 상품, 옵션 | 리포지토리로 직접 저장한다. 재고는 주문 수량보다 넉넉하게 둔다 | 주문을 성공시키기 위한 전제일 뿐이다. 재고·포인트 부족으로 실패하면 메시지 검증까지 가지 못한다 |
| 선물 메시지 | 알아보기 쉬운 고정 문자열(예: `"생일 축하해!"`) | 전송된 메시지에 그대로 들어 있는지 찾기 쉽다 |
| 기본 데이터(`V2`) | 쓰지 않는다 | 기본 회원은 카카오 액세스 토큰이 없어서 메시지 발송 대상이 아니다 |

**정리**

- 시나리오 6과 같이 `RANDOM_PORT`라 `@Transactional` 롤백이 되지 않는다. `@AfterEach`에서 외래키 순서대로(주문 → 옵션 → 상품 → 카테고리 → 회원) 지운다.
- `@MockitoBean`으로 바꾼 목은 테스트마다 초기화되므로 따로 정리하지 않는다.

#### 검증 전략

- **무엇을**
  1. 주문이 생성된다: `POST /api/orders`가 `201 Created`이고 응답 `message`가 보낸 선물 메시지와 같다.
  2. 카카오 메시지가 **한 번** 전송된다.
  3. 받는 대상이 **받는 사람**이다. 주문자 자신이 아니다. 카카오 메시지는 카카오 액세스 토큰 주인에게 가므로, 전송에 쓴 토큰이 받는 사람의 카카오 액세스 토큰인지로 확인한다.
  4. 전송된 내용에 선물 메시지가 들어 있다.
- **어떻게**: 카카오 메시지 발송 클라이언트를 목으로 바꾸고, `ArgumentCaptor`로 전송 요청을 잡아서 받는 대상과 내용을 확인한다. 실제 카카오 API는 호출하지 않는다.
- **검증하지 않는 것**
  - 메시지 템플릿의 정확한 문구·이모지·줄바꿈("🎁 선물이 도착했어요!" 등). 문구는 바뀌기 쉽고, 시나리오는 "선물 메시지가 담긴 메시지가 전송된다"만 요구한다.
  - 카카오 API의 요청 형식(URL, `template_object` JSON). 이건 카카오 클라이언트 자체를 테스트할 일이다.
  - 재고·포인트 차감. 시나리오 1·2에서 확인한다.
  - 발송이 실패해도 주문이 유지되는지. 별도 시나리오로 다룰 내용이다.

#### 주요 의사 결정

| 결정 | 선택 | 이유 |
|---|---|---|
| 카카오 API 처리 | 실제 호출하지 않고 우리 쪽 클라이언트(`KakaoLoginClient`, 메시지 발송 클라이언트)를 `@MockitoBean`으로 바꾼다 | 실제 호출은 키·카카오 계정·네트워크가 필요하고, 테스트할 때마다 진짜 메시지가 간다. URL이 코드에 `kapi.kakao.com`으로 고정돼 있어 WireMock 같은 가짜 서버로 돌리려면 설정부터 바꿔야 한다 |
| 목으로 바꾸는 위치 | HTTP 요청 단계가 아니라 클라이언트 클래스 단계 | 검증하려는 것은 "누구에게, 무엇을 보내는가"라는 우리 서비스의 판단이지 카카오 요청 형식이 아니다 |
| 로그인 Given | 카카오 로그인 콜백 API를 실제로 호출한다(카카오 통신만 목) | 리포지토리에 카카오 토큰을 직접 넣으면 "카카오 로그인 회원"이라는 상태를 테스트가 흉내 내는 것이 된다. 콜백을 거치면 로그인 흐름이 바뀌어도 함께 확인된다 |
| 받는 사람 확인 | 받는 사람을 따로 만들고, 전송 대상이 주문자가 **아님**까지 확인한다 | 현재 버그가 바로 "본인에게 감"이다. 받는 사람만 확인하면 주문자=받는 사람인 데이터에서 버그를 놓칠 수 있다 |
| 실패하는 테스트 처리 | 테스트는 작성하되 `@Disabled("🚧 현재 코드와 불일치: …")`로 둔다 | 지금은 `receiverId`를 무시하고 주문자의 카카오 액세스 토큰으로 보내서 실패한다. 빌드는 깨지지 않게 하면서 목표 동작을 코드로 남기고, 수정할 때 `@Disabled`를 지운다 |
| 테스트 언어·클라이언트 | Java + `TestRestTemplate` | 시나리오 6과 같다 |

#### 받는 사람 지정 방식 (결정됨)

- 받는 사람은 **회원 ID**로 지정한다. 주문 요청에 `receiverId`를 추가한다: `{ optionId, quantity, message, receiverId }`.
- 그래서 받는 사람도 카카오 로그인한 회원이어야 메시지를 받을 수 있다(카카오 액세스 토큰이 있어야 한다).

### 사용자 스토리 : 회원이 위시 아이템을 추가한다 (US-W1, US-W2)
### 시나리오 6 - 위시에 추가한 상품이 위시 목록에 보인다

#### 고른 기준

- **현재 코드와 동작이 같은 유일한 시나리오다.** 시나리오 3·4·5는 "🚧 현재 코드와 불일치"라서 지금 작성하면 실패하는 테스트가 된다. 시나리오 6은 지금 바로 통과해야 하므로, 테스트 환경(서버 기동, 인증, 요청·응답 처리)이 제대로 갖춰졌는지 확인하는 첫 테스트로 알맞다.
- **외부 의존성이 없다.** 카카오 API(시나리오 5)나 여러 엔티티를 함께 바꾸는 흐름(시나리오 1~4의 주문)과 달리 회원·상품·위시만 있으면 된다.
- **인증이 필요한 API를 거친다.** 위시 API는 `Authorization: Bearer <토큰>`이 필요하다. 여기서 "회원 가입 → 토큰 받기 → 인증 요청"을 한 번 만들어 두면 주문 시나리오에서 그대로 다시 쓸 수 있다.
- **두 API를 이어서 확인한다.** `POST`가 성공했다는 응답만 보는 것이 아니라 `GET`으로 다시 조회해서 실제로 저장됐는지 확인한다. 리팩터링으로 저장 방식이나 조회 쿼리가 바뀌어도 회원이 보는 결과는 같아야 한다는 것을 지켜 준다.

#### 테스트 데이터 전략

| 데이터 | 준비 방법 | 이유 |
|---|---|---|
| 회원 + 토큰 | 회원 가입 API(`POST /api/members/register`)로 테스트마다 **새 회원**을 만들고, 응답의 `token`을 쓴다. 이메일은 겹치지 않게 만든다(예: UUID 붙이기) | 새 회원은 위시가 하나도 없으므로 Given "아직 위시에 담지 않았다"가 따로 확인하지 않아도 보장된다. 토큰도 실제 발급 경로로 받는다 |
| 카테고리, 상품 | `CategoryRepository`·`ProductRepository`로 테스트 안에서 직접 저장한다 | 상품은 이 시나리오의 전제일 뿐 검증 대상이 아니다. 상품 생성 API는 "옵션 최소 1개" 규칙 등으로 리팩터링 중 요청 형식이 바뀔 가능성이 높아서, API로 만들면 위시와 상관없는 이유로 이 테스트가 깨진다 |
| 기본 데이터(`V2`) | 쓰지 않는다 | `user1`은 이미 상품 1·3을 위시에 담고 있다. ID와 기존 데이터에 의존하면 `V2`가 바뀔 때 테스트가 깨지고, "아직 담지 않았다" 조건도 직접 맞춰야 한다 |

**정리**

- `@SpringBootTest(webEnvironment = RANDOM_PORT)`로 실제 서버를 띄우고 HTTP로 요청한다. 이 경우 요청이 다른 스레드에서 처리되므로 테스트 메서드의 `@Transactional` 롤백이 적용되지 않는다.
- 그래서 `@AfterEach`에서 이 테스트가 만든 데이터를 외래키 순서대로(위시 → 상품 → 카테고리 → 회원) 리포지토리로 지운다.
- `@DirtiesContext`로 매번 컨텍스트를 새로 띄우는 방식은 느려서 쓰지 않는다. 인메모리 H2라 테스트 실행이 끝나면 DB도 사라진다.

#### 검증 전략

- **무엇을**: 위시 목록 조회 결과(`content`)에 방금 추가한 상품의 `productId`가 있는지 확인한다.
- **어떻게**
  1. `POST /api/wishes`가 `201 Created`인지 먼저 확인한다. 시나리오의 Then은 아니지만, 추가가 실패했는데 조회 단계에서 원인이 헷갈리지 않도록 빨리 실패시키는 용도다.
  2. `GET /api/wishes`가 `200 OK`인지 확인한다.
  3. `content`의 `productId` 목록에 Given에서 만든 상품 ID가 **포함**되는지 확인한다.
- **확인 방법은 API 응답만 쓴다.** DB를 직접 조회하지 않는다. 인수 테스트는 회원이 보는 결과를 기준으로 하고, 내부 저장 방식은 리팩터링으로 바뀔 수 있기 때문이다.
- **검증하지 않는 것**: 위시 `id` 값, 목록 개수(`totalElements == 1`), 정렬 순서, `name`·`price`·`imageUrl` 같은 나머지 필드. 시나리오가 요구하는 것은 "포함"이므로 그 이상을 걸면 시나리오와 무관한 변경에 테스트가 깨진다.

#### 주요 의사 결정

| 결정 | 선택 | 이유 |
|---|---|---|
| 테스트 범위 | MockMvc가 아니라 `RANDOM_PORT` + 실제 HTTP 요청 | 인수 테스트는 필터·직렬화·헤더 처리까지 포함한 실제 동작을 확인해야 한다 |
| HTTP 클라이언트 | Spring 기본 `TestRestTemplate`(또는 `RestClient`) | RestAssured 등은 현재 의존성에 없다. 테스트 하나를 위해 의존성을 늘리지 않는다 |
| 테스트 언어 | Java | 프로덕션 코드가 전부 Java다. Kotlin 플러그인이 있지만 `src/main/kotlin`은 비어 있다 |
| Given 준비 경로 | 회원은 API, 상품은 리포지토리 | 토큰은 실제 발급 경로를 거쳐야 의미가 있고, 상품은 검증 대상이 아니라서 변경 가능성이 큰 API를 피했다 |
| 비교 기준 | 상품 이름이 아니라 `productId` | 이름은 바뀌거나 겹칠 수 있다. ID가 "그 상품"을 가장 정확히 가리킨다 |
| 단언 강도 | "같다"가 아니라 "포함한다" | 시나리오 문장을 그대로 옮겼다. 정렬·페이징 기본값이 바뀌어도 깨지지 않는다 |

### 사용자 스토리 : 회원이 이메일로 로그인한다 (US-A2)
### 시나리오 7 - 이메일 형식이 아닌 값으로 로그인하면 400과 기본 에러가 응답된다
### 시나리오 8 - 가입되지 않은 이메일로 로그인하면 400과 로그인 실패 메시지가 응답된다

#### 고른 기준

- **로그인 실패가 어떤 단계에서 걸러지는지 구분할 수 있다.** 같은 400이라도 형식 오류는 입력값 검증(`@Email`)에서, 없는 회원은 로그인 로직에서 걸린다. 응답 본문으로 둘을 구분해 확인한다.
- **현재 코드와 동작이 같다.** 두 시나리오 모두 지금 바로 통과해야 한다. 처음에는 없는 이메일을 `404`로 하려 했으나, 회원 잘못은 `400`이라는 기준(AGENTS.md)과 사용자 스토리에 맞춰 `400`으로 정했다.
- **외부 의존성이 없다.** 카카오 없이 가입·로그인 API만 쓴다.

#### 테스트 데이터 전략

| 데이터 | 준비 방법 | 이유 |
|---|---|---|
| 가입된 회원 | 가입 API(`POST /api/members/register`)로 `test@gmail.com` / `password123`을 만든다 (`registerMember(email, password)`) | Given이 "가입한 회원이 있다"이므로 실제 가입 경로를 거친다. 시나리오에 적힌 값을 그대로 쓴다 |
| 로그인 요청 (시나리오 7) | 이메일 `test.com`, 비밀번호 `password123` | `@`가 없어서 이메일 형식이 아니다. 로그인 로직 전에 입력값 검증에서 걸린다 |
| 로그인 요청 (시나리오 8) | 이메일 `test2@gmail.com`, 비밀번호 `password123` | 형식과 비밀번호는 맞지만 가입되지 않은 이메일이다. 입력값 검증을 지나 "없는 회원" 판단까지 간다 |
| 기본 데이터(`V2`) | 쓰지 않는다 | 시나리오에 필요 없다 |

**정리**

- 가입한 회원은 `AcceptanceTest.cleanUp()`이 지운다. 이메일이 고정값이라 정리가 안 되면 다음 테스트에서 "이미 가입된 이메일"로 실패한다.

#### 검증 전략

- **무엇을**
  - 시나리오 7: 상태가 `400`이고, 본문이 Spring 기본 에러 JSON이며 `error`가 `"Bad Request"`다.
  - 시나리오 8: 상태가 `400`이고, 본문이 `"Invalid email or password."`다.
- **어떻게**: 로그인 API 응답만 본다. 두 응답의 형식이 달라서(JSON / 문자열) 문자열로 받고, 시나리오 7만 JSON으로 읽는다.
- **검증하지 않는 것**
  - Spring 기본 에러의 `timestamp`, `path`, `status` 필드.
  - 비밀번호 불일치·카카오 회원 로그인. 별도 시나리오다.

#### 주요 의사 결정

| 결정 | 선택 | 이유 |
|---|---|---|
| 없는 이메일의 상태 코드 | `404`가 아니라 `400` | 회원 잘못은 `400`이라는 기준과 사용자 스토리를 따른다. 응답만으로 가입 여부를 알 수 없게 하는 효과도 있다 |
| 형식 오류의 "올바른 메시지" | `error: "Bad Request"` | 지금 Spring 기본 에러에는 형식 오류를 설명하는 메시지가 없다(`server.error.include-message` 기본값). `"Invalid email or password."`가 아닌 것으로 입력값 검증 단계에서 걸렸음을 확인한다 |
| 응답 타입 | `String` | 실패 응답이 JSON일 때와 `text/plain`일 때가 있어 `JsonNode`로 받으면 문자열 응답에서 테스트가 깨진다 |
