# 인수 조건 · 인수 테스트 작성 기준

일반적인 테스트 작성법은 적지 않았다. 아래는 이 저장소에서 사용자가 **두 번 이상 고친 것**과, 그 결과 정해진 기준이다.

## 0. 반드시 지킬 규칙

1. **시나리오에는 Given, When, Then, And가 모두 있어야 한다.** 하나라도 빠지면 시나리오를 완성하지 않은 것이다. 덧붙일 조건이나 결과가 떠오르지 않으면 지어내지 말고 사용자에게 묻는다.
2. **사용자 스토리에는 시나리오가 1개 이상 있어야 한다.** 시나리오 없이 스토리 제목만 추가하지 않는다.
3. **테스트는 사용자가 입력한 기대 동작대로 쓴다. 지금 코드에서 실패해도 그렇다.** 테스트가 통과하도록 기대값·상태 코드·단언을 현재 코드에 맞춰 바꾸지 않는다. 실패하는 테스트는 `@Disabled("🚧 …")`로 꺼 둔다(1절).
4. **리팩터링 후에도 지켜야 할 목표 동작을 기준으로 쓴다.** 시나리오, 테스트 전략, 테스트 코드 모두 같다. 지금 코드가 어떻게 동작하는지는 🚧 메모에만 적는다.
5. **테스트 코드는 사용자가 시나리오와 인수 조건을 명시한 뒤에만 쓴다.** 아래 순서를 지킨다.

## 작업 순서와 멈출 지점

1. **초안을 만든다.** 인수 조건과 Given/When/Then/And 시나리오 초안을 보여 준다. 현재 코드와 다른 곳(🚧 후보), 정해지지 않은 것도 함께 적는다.
2. **멈추고 기다린다.** 사용자가 초안을 확인하고 **구체적인 테스트 시나리오와 인수 조건을 직접 명시할 때까지** 테스트 코드를 쓰지 않는다. 테스트 파일 생성·수정, 테스트 실행도 하지 않는다.
   - "좋아요", "진행해", "Approve"처럼 승인만 한 답은 명시가 아니다. 어떤 시나리오와 인수 조건으로 확정할지 사용자의 말로 받는다. 승인만 받았으면 확정할 시나리오와 인수 조건을 다시 보여 주고 그대로 확정할지 묻는다.
   - 사용자가 초안과 다르게 적으면 사용자가 쓴 것을 따른다.
3. **확정된 내용을 문서에 반영한다.** `user-stories.md`(시나리오)와 `test-strategy.md`(4절)에 사용자가 명시한 그대로 적는다.
4. **테스트 코드를 쓰고 실행한다.** 확정된 시나리오와 인수 조건에 없는 단언은 더하지 않는다.

## 1. 시나리오가 현재 코드와 다를 때 — 어느 쪽에도 맞추지 않는다

인수 테스트는 **리팩터링 후의 목표 동작**이다. 지금 코드 동작이 아니다.

- 시나리오를 현재 코드에 맞춰 고치지 않는다. 코드를 시나리오에 맞춰 고치지도 않는다(이번 단계에서 코드는 수정하지 않는다).
- 문서(`user-stories.md`)에 아직 적히지 않은 불일치를 찾으면 **멈추고 알린다.** 무엇이, 어디서(파일:줄), 지금은 어떻게 동작하는지를 함께 적는다.
- 사용자가 목표 동작으로 확정하면:
  - 시나리오 아래에 `> 🚧 현재 코드와 불일치: <지금 실제로 어떻게 되는지>`를 한 줄 단다.
  - 테스트는 **목표 동작으로** 쓰고 `@Disabled("🚧 현재 코드와 불일치: <같은 이유>")`로 꺼 둔다. 빌드는 깨지지 않고 목표는 코드로 남는다. 고칠 때 `@Disabled`만 지운다.
  - `@Disabled`를 잠시 풀고 돌려서 **🚧에 적은 바로 그 이유로** 실패하는지 확인한 뒤 다시 꺼 둔다. 다른 이유(데이터 준비 실패 등)로 실패하면 테스트가 틀린 것이다.
- 재고 부족·포인트 부족 같은 **회원의 잘못은 `400 Bad Request`**다. 지금 주문 API는 500을 주지만 시나리오에는 400으로 쓴다. "결제가 거절된다"처럼 상태 코드가 빠진 Then도 테스트에서는 400으로 확인한다.

## 2. 정해지지 않은 것을 TODO로 남기지 않는다

- 시나리오에 필요한 결정이 없으면(예: 요청에 어떤 필드를 넣을지) 초안에 "아직 정하지 않은 것"으로 미루거나 `fail(...)`·TODO로 막아 두지 않는다. **선택지를 들고 바로 묻는다.**
- 답을 받으면 `user-stories.md`(시나리오), `test-strategy.md`, `open-questions.md`(결정 기록), 필요하면 `glossary.md`까지 함께 고친다. 답이 바로 안 나오면 `open-questions.md`에만 올린다.
- 이미 정해진 것 — 다시 묻지 않는다:
  - **받는 사람은 회원 ID로 지정한다.** 주문 요청: `{ optionId, quantity, message, receiverId }`. 그래서 받는 사람도 카카오 로그인 회원이어야 한다.
  - 카카오 메시지가 받는 사람에게 갔는지는 `KakaoMessageClient`에 넘어간 **카카오 액세스 토큰**으로 확인한다(메시지는 토큰 주인에게 간다). 받는 사람 토큰과 **같고**, 주문자 토큰과 **다른지** 둘 다 단언한다. 지금 버그가 "주문자 본인에게 감"이라서 앞의 것만으로는 놓칠 수 있다.
  - 메시지 문구·이모지, 카카오 요청 형식(URL, `template_object`)은 검증하지 않는다.

## 3. 테스트 전략 문서 — 네 절을 모두 쓴다

위치: `docs/work/02-acceptance-test/test-strategy.md`. 시나리오마다 아래 네 절을 **모두** 쓴다. 고른 기준도 빼지 않는다.

1. **고른 기준** — 어떤 스토리·시나리오를 왜 골랐는가. 굵은 글씨 한 문장 + 근거로 쓴다. 이 프로젝트에서 쓰는 기준 예: 현재 코드와 동작이 같은가(🚧 여부), 잘못된 동작을 판단할 수 있는가, 도메인 핵심 기능인가, 외부 의존성(카카오)이 있는가, 다음 시나리오에서 다시 쓸 준비(인증 흐름 등)를 만드는가.
2. **테스트 데이터 전략** — 데이터마다 `데이터 | 준비 방법 | 이유` 표, 그리고 정리 방법.
3. **검증 전략** — 무엇을 / 어떻게 / **검증하지 않는 것**.
4. **주요 의사 결정** — `결정 | 선택 | 이유` 표.

- 사용자가 이미 쓴 줄은 덮어쓰지 않는다. 사용자가 쓴 고른 기준이 있으면 그대로 두고 빈 항목(`- ****`, `-`)만 채운다. "다시 넣어 줘"는 비어 있는 자리를 채우라는 뜻이다.
- 🚧 시나리오는 맨 앞에 "지금 코드로는 테스트가 실패하는 것이 맞다. 아래는 목표 동작 기준이다"를 붙인다.

## 4. 도구는 Java + TestRestTemplate으로 고정

- 2026-11-22에 Cucumber + RestAssured + Kotlin으로 바꾸려다 **사용자가 롤백했다.** 사용자가 다시 요청하지 않으면 제안하지 않는다.
- 의존성을 더하지 않는다. `spring-boot-starter-test`에 있는 JUnit 5, AssertJ, Mockito, `TestRestTemplate`만 쓴다.
- 사용자 스토리 하나당 테스트 클래스 하나, `AcceptanceTest`를 상속한다.
  - 클래스 `@DisplayName` = 스토리 제목, 메서드 `@DisplayName` = `"시나리오 N. <시나리오 제목>"`, 메서드 이름 = 시나리오 제목을 `_`로 이은 한글.
  - 본문 주석에 Given/When/Then/And 줄을 `user-stories.md`에서 **그대로** 옮긴다.
  - 🚧 시나리오에서 Then이 여러 개면 `SoftAssertions.assertSoftly`로 묶어 실패 이유가 한 번에 다 보이게 한다.

## 5. 테스트 데이터 준비

`src/test/java/gift/acceptance/AcceptanceTest.java`의 도우미를 쓴다. 새 엔티티가 필요할 때만 여기에 도우미를 더한다.

| 데이터 | 방법 | 이유 |
|---|---|---|
| 일반 회원 + 토큰 | `registerMember()` — 가입 API, 이메일은 UUID로 매번 새로 | 새 회원은 포인트 0, 위시·주문 없음이라 "아직 ~하지 않았다" Given이 저절로 맞는다 |
| 카카오 로그인 회원 | `kakaoLogin("kakao-access-token-<역할>")` — 콜백 API를 실제로 호출, `KakaoLoginClient`만 목 | 회원 생성·카카오 토큰 저장·토큰 발급을 실제 코드로 거친다. 리포지토리에 토큰을 직접 넣지 않는다 |
| 포인트 | `setPoint(member, amount)` — 새 회원에게만 | 회원이 포인트를 충전·조회하는 API가 없다 |
| 카테고리·상품·옵션 | `createProduct(price, stock)` — 리포지토리로 저장 | 검증 대상이 아니고, 상품 생성 API는 "옵션 최소 1개" 규칙 때문에 바뀔 예정이다 |
| `V2` 기본 데이터 | **쓰지 않는다** | `user1`은 이미 위시가 있고, 기본 회원에게는 카카오 액세스 토큰이 없다 |

- 결과 확인은 **API 응답**으로 한다. 재고는 `stockOf(product)`(옵션 목록 API). 포인트만 조회 API가 없어서 `pointOf(member)`(리포지토리)를 쓴다.
- 금액·재고는 시나리오에 적힌 숫자를 그대로 쓴다(15,000원, 재고 15개, 포인트 20,000 등).
- `RANDOM_PORT`라 `@Transactional` 롤백이 안 된다. `AcceptanceTest.cleanUp()`이 외래키 순서(주문 → 위시 → 상품(옵션 cascade) → 카테고리 → 회원)로 지운다. 새 종류의 데이터를 만들면 여기에도 추가한다. `@DirtiesContext`는 쓰지 않는다.
- 목은 `KakaoLoginClient`, `KakaoMessageClient` 둘뿐이고 `AcceptanceTest`에만 둔다. 하위 클래스에 `@MockitoBean`을 더하면 스프링 컨텍스트가 따로 뜬다.
- 용어 주의: `Option.quantity`와 `OptionResponse.quantity`는 **재고**다. 주문 요청의 `quantity`는 **주문 수량**이다. 문서·주석·`@DisplayName`에서는 용어 사전(`docs/glossary.md`) 이름을 쓴다.

## 6. 실행

Windows는 `gradlew.bat`, 그 외는 `./gradlew`.

```powershell
.\gradlew.bat test --tests "gift.acceptance.*"
```

```powershell
.\gradlew.bat test --tests "gift.acceptance.OrderAcceptanceTest"
```

- 결과는 `build/reports/tests/test/index.html`. 🚧 시나리오는 skipped로 나오는 것이 정상이다.
- `Mockito is currently self-attaching…` / `A Java agent has been loaded dynamically` 경고는 `@MockitoBean` 때문에 나오는 JDK 21 경고다. 테스트 결과와 상관없다.
- 카카오 키(`KAKAO_CLIENT_ID` 등)는 필요 없다. 카카오 통신은 전부 목이다.
